# Задание 14. «Голосовые, которые можно читать»

## Цель

Разработать на Go HTTP-сервис, который принимает аудиофайлы, быстро создаёт задания на распознавание и выполняет тяжёлую операцию локально в фоне. После завершения пользователь получает расшифровку и может искать по всем сохранённым текстам.

Собственную нейросеть обучать не нужно: требуется готовая **локальная** speech-to-text (STT) модель — например, Whisper. Использование облачного API распознавания не допускается.

## Основной поток

```text
аудиофайл → HTTP upload → создание задания → ограниченная очередь
                                                ↓
                                         worker pool → локальная STT-модель
                                                ↓
                                     постоянное хранилище текста → поиск
```

## Обязательные функциональные требования

### Локальное распознавание

- Распознавание выполняется локально во время демонстрации.
- Модель подключается через библиотеку, локальный процесс, отдельный локальный сервис или другой обоснованный механизм.
- Ошибка обработки одного файла не должна останавливать worker или приложение.

### Загрузка аудио

- Должен существовать endpoint, эквивалентный `POST /audio`.
- После сохранения файла API создаёт задание и сразу возвращает его идентификатор; HTTP-обработчик не ждёт результата STT.
- Загрузка ограничивает максимальный размер входных данных и сохраняет файл потоково, без неограниченного `io.ReadAll`.
- Минимально поддерживается распространённый формат `wav`; окончательный список поддерживаемых форматов описывается в README реализации.

Пример ответа:

```json
{"jobId":"8d3b6a4e"}
```

### Задания и состояния

У задания хранятся минимум:

- идентификатор;
- исходное имя файла;
- статус;
- время создания, начала и окончания обработки;
- ошибка при неуспехе;
- текст расшифровки.

Допустимые статусы:

```text
queued → processing → completed
                 └→ failed
```

### Очередь и worker pool

- После создания задание помещается в ограниченную очередь.
- Количество worker'ов ограничено и задаётся конфигурацией (например, `workers=2`).
- Нельзя создавать бесконтрольную goroutine на каждый загруженный файл.
- Размер очереди конфигурируется (например, `queue_size=50`).
- При заполненной очереди сервис возвращает предсказуемый отказ (`503 Service Unavailable` или `429 Too Many Requests`); выбранный вариант фиксируется в README реализации.
- Worker переводит задание в `processing`, запускает локальную STT-модель, сохраняет результат и переводит его в `completed`; при ошибке — в `failed` с текстом ошибки.

### Постоянное хранение и перезапуск

- Задания и результаты переживают перезапуск процесса; допустимы SQLite, PostgreSQL или другое постоянное хранилище.
- Аудиофайлы допускается хранить в файловой системе или другом локальном хранилище.
- После рестарта пользователь должен видеть завершённые задания, читать транскрипты и выполнять поиск.
- Необходимо выбрать и документировать стратегию для заданий, оставшихся в `queued` или `processing` при аварийной остановке (например, вернуть их в очередь при запуске).

### Чтение результатов и поиск

Минимальный HTTP API:

| Метод и путь | Назначение |
| --- | --- |
| `POST /audio` | Загрузить аудио и создать задание |
| `GET /jobs` | Получить список заданий |
| `GET /jobs/{id}` | Получить состояние задания |
| `GET /jobs/{id}/transcript` | Получить готовую расшифровку |
| `GET /search?q=...` | Найти среди завершённых расшифровок |

Если расшифровка ещё не готова, API результата должен вернуть корректный статус/ошибку, а не пустой успешный ответ.

Поиск — минимум регистронезависимый поиск подстроки только по завершённым расшифровкам. В выдаче должны присутствовать `jobId`, `fileName` и фрагмент текста.

## Нефункциональные требования

- Конкурентный доступ HTTP-обработчиков и worker'ов к заданиям должен быть потокобезопасным, без data race.
- Обработка `SIGINT` и `SIGTERM`: перестать принимать новые задания, корректно остановить HTTP-сервер и workers, сохранить консистентное состояние и определить судьбу незавершённых задач.
- Длительные операции должны по возможности принимать `context.Context`; ограничение модели/процесса на отмену необходимо описать.
- Проект обязан проходить:

```bash
go test ./...
go test -race ./...
```

## Исследование производительности

Главная исследовательская часть — влияние числа worker'ов на обработку локальной STT-моделью.

### Методика

- Использовать одинаковый набор файлов во всех прогонах (рекомендуется 10 файлов длительностью 30–60 секунд).
- Провести минимум три эксперимента: `workers=1`, `workers=2`, `workers=4`.
- Для каждого запуска измерить общее время всего набора, среднюю длительность обработки одного задания и пиковое/характерное потребление памяти.
- В README реализации указать реальную модель, параметры запуска и характеристики компьютера.

### Анализ

Нужно различать:

- **Latency** — время конкретного задания от `processing` до `completed`.
- **Throughput** — сколько заданий обработано за заданное время.

В выводах объяснить реальные измерения: рост throughput при увеличении параллелизма, возможное отсутствие линейного ускорения, конкуренцию экземпляров модели за CPU/GPU и память, а также точку, после которой увеличение worker'ов почти не помогает или ухудшает результат.

Следует отдельно показать backpressure: когда входящий поток заданий выше скорости распознавания, очередь растёт до лимита, после чего сервис отказывает новым запросам, не накапливая память бесконтрольно.

## Демонстрация

На защите показать:

- загрузку корректного аудиофайла и немедленный `jobId`;
- статусы `queued`, `processing`, `completed` через HTTP;
- получение готового текста;
- поиск слова/фразы по нескольким расшифровкам;
- ошибку обработки некорректного файла;
- параллельную работу нескольких worker'ов;
- заполнение очереди и отказ/backpressure;
- сохранность результатов после перезапуска;
- корректное завершение приложения;
- таблицу и анализ экспериментов для разных значений числа worker'ов.

## Критерий готовности

Сервис соответствует ТЗ, если он написан на Go, имеет описанный HTTP API, ограниченную очередь и worker pool, использует локальную STT-модель, надёжно хранит статусы/тексты, безопасен при конкурентном доступе, корректно завершает работу и содержит документированные реальные измерения производительности.
